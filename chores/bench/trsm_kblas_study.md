# TRSM 探索实验：kblas 库能力实测

日期：2026-09-02，计算节点 cn22965（16 散核 vCPU，无 numactl）

## 关键事实：kplblas 库里有 cblas_dtrsm

`kblas.h` 声明 + `libkplblas.so` 导出确认：**cblas_dtrsm 存在且可调用**（还有 dtrmm、dsyrk 等全套，以及线程控制 API `BlasSetNumThreads/BlasGetNumThreads`）。l_trsm 一行调用即合法（编译命令本身链接 kblas）。

## 结论

1. **kblas 线程数 > vCPU 数时灾难性崩塌**（38 线程挤 16 核 → 50× 性能损失）。这是 libomp（kblas 内部 OpenMP 运行时）过订阅的伪影，仅存在于 dev 集群；评测机 38 线程 ↔ 38 核一一对应不会发生。我们的 libgomp 代码过订阅无此问题（CONV OMP=38 正常）。
2. **库的 dtrsm 本身很强**（内部即分块 GEMM 算法），dev OMP=16 下 case2 达 451 GFLOPS，接近其自身 dgemm 水平。评测机上预估 500~1200 GFLOPS。
3. 单核 dgemm 43.5 GFLOPS → 单核峰值约 64 GFLOPS（SVE），38 核理论 ~1600 GFLOPS。
4. dev 测量方法：**OMP=16 + 无 numactl** 是评测环境（38 核单 NUMA）的最佳近似；OMP=38 在 dev 上会触发崩塌，不能用于评测判断。
5. 机会点：
   - case1：L 仅 2 MB，可驻留 L2 → 列并行自定义内核有望 1000+ GFLOPS（每线程独立前代，L 从 L2 全速读）
   - case2/3：L 超出 L2 → 库的分块 GEMM 路径已是正确形态，需按形状定制分块策略或用对角块求逆 + 大 GEMM 才能超过它
   - l_trsm 内按 (m,n) 形状分支调度是合法且必要的

## 自研路线实验记录（v1-v3，2026-09-02）

### v1: 列面板并行前代（case1 专用，m≤1024）

每线程独立处理一段列面板（W=32），L 缓存驻留重复读。结果 case1 仅 18.4 GFLOPS（库 232）。
诊断：累加器 s 在栈内存，每 k 步 3 次 L1 访存配 1 次 FMA，微内核效率低（~1.5 GFLOPS/线程）；
且 dev 上 L 页被 bench 多线程 first-touch 撒在 16 个 NUMA，重复读全远程。

### v2: v1 + 线程私有紧凑 L 副本（first-touch 本地化）

case1 提升到 24.2 GFLOPS（W 扫描 16/32/64/128 → 15.0/24.2/18.6/6.7），远程 L 只是次要因素，
微内核效率（s 在内存）是主因。仍远低于库。

### v3: 分块右视 + 我们的 OpenMP + 每线程单线程 kblas（BlasSetNumThreads(1)）

- 关键验证：`BlasSetNumThreads(1)` 有效（单线程 42.4 GFLOPS），且不设它时并发调用会触发
  libomp 嵌套（"may hang" 警告 + 47 GFLOPS 灾难）
- 结构：k 串行块扫描；对角块 = 列条带并行单线程 cblas_dtrsm；更新 = 行带并行单线程 cblas_dgemm
- 结果（bm 扫描 128/256/512，取最佳）：case1 95.3 / case2 136.4 / case3 204.8 —— 全输库
- 根因：行带划分导致每线程全读 X_k（广播模式），case2 总流量 ~1.45 GB，而 dev 散核聚合带宽
  仅 ~2-3 GB/s。16 并发单线程 dgemm 实测仅 7-11 GFLOPS/线程（exp_bset 验证）
- 结论：dev 散核环境惩罚一切高流量结构；库的结构流量最小所以赢。v3 结构在评测机
  （本地内存 + 38 核）的理论上限未被证伪，但 dev 无法验证

### v4-v6（2026-09-02 晚）：自适应分块 + SVE 内核 + 争用鲁棒性

**关键事实发现：**
1. **920F 的 SVE 是 512-bit**（svcntd=8，每 z 寄存器 8 个 double）——不是通常假设的 256-bit。
   v4 硬编码 4-double 步长导致 case1 出错（err 0.5）；v5 面板宽度改为运行时 8×svcntd 后 PASS
2. **库对共租户争用极其敏感**：quiet 时段 cblas_dtrsm = 232/434/214 GFLOPS，共租户负载下崩到
   21/86/45（4-10×）。机制推测与其 libomp 自旋 barrier 有关。我们的结构（libgomp + 单线程
   BLAS 调用，无内部 barrier）对争用免疫
3. **case1 走分块路径完胜自研内核**：bm=512 时分块退化为"列条带并行单线程 dtrsm"，
   133 GFLOPS（contended）vs 自研 SVE 面板内核 39-54。教训：不做朴素面板扫描与厂商打包
   微内核拼计算密度，做编排者

**v6 结构（当前提交）：**
- 全形状走分块右视：对角块 = 列条带并行单线程 cblas_dtrsm；更新 = 形状自适应划分
  （below<n → 列划分广播 L_ik；否则行划分广播 X_k，广播小操作数切分大操作数）
- BlasSetNumThreads(1) + 我们自己的 OpenMP
- colpanel SVE 内核保留但默认关闭（TRSM_SMALL_M=0）

**v6 成绩（重争用条件下 vs 库同 job）：**

| case | v6 (bm=512) | 库 | 优势 |
| --- | --- | --- | --- |
| 1 | 105-133 | 21-26 | 4-5× |
| 2 | 168-220 | 75-98 | 2× |
| 3 | 172-185 | 44-53 | 3.5-4× |

（quiet 条件下的对比待看门狗 job 结果；库 quiet 数据 232/434/214 作参考基准）

**评测机推演（38 核单 NUMA 本地内存，无争用）：**
- 单线程 dgemm 43.5 GFLOPS 实测 → 我们结构上限 38×43 ≈ 1634 GFLOPS
- 评测机无共租户、无远程访存税，v6 三个 case 预计数百 GFLOPS 量级

## v7-v10（2026-09-03）：评测命令坍缩机制解剖与防御

**问题起点**：v6 在评测命令（`OMP_NUM_THREADS=38 numactl -N 1`）下 = 40.2s，
比榜首 20.47s 还差 2 倍——38 线程被合流到单核后，libgomp barrier 风暴使并行比串行慢 5-30×。

**机制解剖（逐步逼近）**：
1. v7（10ms FMA 探针）→ 130s 灾难：探针在合流生效前测到"健康并行"。
   合流有秒级延迟（内核周期性评估），短探针必然被骗。
2. v8（真实工作区域在线检测 + 串行回退）→ 串行回退后反而 0.6 GFLOPS：
   **污染是进程级粘性的**——"试并行再退串行"的试探本身触发降速，污染后串行也废。
   且 bench 自己的 B 生成阶段（38 个 libomp 线程 × 秒级 dgemm）就可能先把进程污染掉。
3. v9（一次决策不回头）→ 决策成了硬币：8 线程 × 100-300ms 探针有时测不到延迟生效的合流。
4. **v9d 的 sched_getcpu 直接观测**：8 线程同步采样各自所在 CPU，全部同核 = 被合流（直接
   看见机制本身，与天气/共租户忙闲无关）。确认了"标记"模型：**重度超订（大量线程×百毫秒）
   触发粘性标记；被标记后任何多线程都被压到配核；8 线程不触发标记（借闲核真 8× 跑）**。
   同一进程里 8 线程探针全速、38 线程正式工作瞬间灾难，是铁证。

**v10 设计（当前提交）**：
1. **正式工作最多 8 线程**——即使中途被合流也只是单核上 ~2.4× 串行的温和退化，
   38 线程风暴的灾难下界被结构性消灭（实测最坏 8.3s vs v6 的 95s）。
2. 决策探针与正式工作同为 8 线程（测得即跑得）：
   - 信号一：sched_getcpu 同步采样，8 线程全同核 → 已被合流 → 串行；
   - 信号二：8 线程纯 FMA 吞吐比 < 3（防配额限流容器）→ 串行。
3. 误选串行代价（串行总计 ~6.4-7.6s，仍领先榜首 ~3 倍）≪ 误选重线程并行的坍缩灾难。

**v10 成绩（cn22965，weather 198 GFLOPS）**：

| 环境 | case1/2/3 | 总计 |
| --- | --- | --- |
| 评测命令 ×4 轮 | 251-490 / 2649-5342(一轮 8052) / 3476-4111(一轮 8291) | 典型 ~9.3s |
| OMP=16 无 numactl | 96 / 200 / 213 GFLOPS | ~1.25s |
| OMP=1 纯串行 | 23.1 / 29.6 / 35.0 GFLOPS | ~7.9s |

（评测命令下的坏轮 = bench 自身 B-gen 预污染（case1 R1 8913ms，无解，榜首同样会中）
或中途合流（2.4× 串行，有界）。三案最优组合 6.38s；健康真 38 核机预估 ~2.8s。）

**教训（写进 pitfalls #16）**：
- 深超算亲和域集群上 numactl -N 1 的合流标记机制：重度超订触发、粘性、秒级延迟生效；
  一切"先试后退"策略都会被污染惩罚，决策必须一次完成
- 探针必须与正式执行同构（线程数一致），否则测的不是将要发生的事
- sched_getcpu 同步采样是观测合流机制的唯一直接手段
